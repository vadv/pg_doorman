# Режимы пула

pg_doorman поддерживает два режима пула: `transaction` и `session`. Режим задаётся для пула, при необходимости переопределяется для конкретного пользователя.

Режима `statement` нет.

## Транзакционный режим (рекомендуется)

```yaml
pools:
  mydb:
    pool_mode: "transaction"
```

Поддерживаются:

- Именованные и анонимные подготовленные запросы.
- Pipeline и асинхронный `Flush`.
- Отмена запросов через TLS.

## Сессионный режим

```yaml
pools:
  legacy_app:
    pool_mode: "session"
```

Используйте для клиентов, которым нужны:

- Параметры сессии (`SET search_path`, `SET TIME ZONE`).
- Подписки `LISTEN`.
- Курсоры `WITH HOLD` и advisory-блокировки между транзакциями.

## Переопределение для конкретного пользователя

Режим пула можно переопределить для конкретного пользователя:

```yaml
pools:
  mydb:
    pool_mode: "transaction"
    users:
      - username: "app"
        password: "md5..."
        pool_size: 40
      - username: "admin_tools"
        password: "md5..."
        pool_size: 4
        pool_mode: "session"
```

Полезно, когда одному пользователю (инструменты эксплуатации, миграции) нужна семантика сессии, а основное приложение остаётся в транзакционном режиме.

## Очистка при возврате в пул

По умолчанию включён `cleanup_server_connections: adaptive` без `cleanup_server_query`: pg_doorman очищает сессию только когда видит её изменение, поэтому подготовленные запросы переживают возврат соединения в пул. Это подходящий режим для OLTP-нагрузки на PostgreSQL.

`cleanup_server_query` заменяет встроенную очистку и требует `always`: собственный SQL выполняется при каждом возврате использованного соединения. С `adaptive` он несовместим, и такая конфигурация отклоняется при проверке. Режим дороже для сервера, потому что запрос уходит на каждый возврат. Кешируемые prepared statements pg_doorman готовит заново сам, а клиентские `PREPARE name` и `EXECUTE name` не отслеживает, и если настроенный запрос их освобождает, следующая `EXECUTE` завершится ошибкой. `off` отключает очистку сессии. Незакрытые транзакции откатываются независимо от режима.

`adaptive` не гарантирует полной очистки сессии: временные объекты, подписки `LISTEN` и advisory-блокировки освободит только `always` с подходящим SQL.

Настройки, ограничения и примеры для PostgreSQL и Greengage см. в [справочнике](../reference/pool.md#cleanup_server_connections).
