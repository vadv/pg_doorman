# Режимы пула

pg_doorman поддерживает два режима пула: `transaction` и `session`. Режим задаётся для пула, при необходимости переопределяется для конкретного пользователя.

Режима `statement` нет. В statement-пулинге серверное соединение ротируется после каждого оператора — это вынуждает клиентов отказаться от мульти-statement транзакций и полностью ломает протокол prepared statements. Все оптимизации pg_doorman (кеш prepared statements, прямая передача, строгий FIFO-планировщик) рассчитаны на транзакционный режим. PgBouncer оставляет `statement` для обратной совместимости; Odyssey его не реализует.

## Транзакционный режим (рекомендуется)

```yaml
pools:
  mydb:
    pool_mode: "transaction"
```

Backend-соединение удерживается в течение транзакции и возвращается в пул при `COMMIT`, `ROLLBACK` или неявном завершении.

Именно этот режим даёт ту самую эффективность соединений, ради которой существует pg_doorman: `pool_size` равный 40 обслуживает тысячи клиентов, пока транзакции остаются короткими.

Что работает в транзакционном режиме (там, где большинство пулеров проваливаются):

- Prepared statements. pg_doorman кеширует их в рамках пула, переименовывает имена statement между backend-соединениями и прозрачно повторно готовит запрос. Драйверы, привязанные к `unnamed`-statement (Go pgx, .NET Npgsql, Python asyncpg), работают без настройки.
- Pipelined-батчи и асинхронный поток `Flush`.
- Cancel-запросы поверх TLS.
- `LISTEN` / `NOTIFY` — но только внутри транзакции. `LISTEN` после `COMMIT` отпускает backend, и любые уведомления, доставленные ему после, попадут к тому клиенту, который следующим заберёт это соединение, а не к исходному `LISTEN`-еру. PgBouncer ведёт себя так же; если вам нужен `LISTEN` через несколько транзакций, для этого клиента используйте сессионный режим.

Что в транзакционном режиме **не работает**:

- `SET` и `RESET` вне транзакции. Используйте сессионный режим для клиентов, опирающихся на изменение GUC уровня сессии (`SET TIME ZONE`, `SET search_path` один раз на соединение).
- advisory-блокировки, удерживаемые между транзакциями. Используйте сессионный режим.
- курсоры, удерживаемые вне транзакций (`WITH HOLD`). Используйте сессионный режим.
- `SET LOCAL` работает как ожидается — он ограничен транзакцией.

## Сессионный режим

```yaml
pools:
  legacy_app:
    pool_mode: "session"
```

Backend-соединение удерживается в течение клиентской сессии. В пул возвращается только при отключении клиента.

Используйте, когда:

- Приложение использует состояние уровня сессии (`SET search_path`, `SET TIME ZONE`).
- Приложение использует курсоры WITH HOLD.
- Приложение использует advisory-блокировки между транзакциями.
- Вы переезжаете с немодифицированного PgBouncer-развёртывания, работавшего в сессионном режиме, и хотите подмену один-в-один.

В сессионном режиме `pool_size` фактически равен максимальному числу одновременных клиентов. Размер пула подбирается так, чтобы соответствовать `max_connections` PostgreSQL минус резервы.

## Переопределение для конкретного пользователя

Режим пула можно переопределить для конкретного пользователя:

```yaml
pools:
  mydb:
    pool_mode: "transaction"
    users:
      - username: "app"
        password: "md5..."
        pool_size: 40
      - username: "admin_tools"
        password: "md5..."
        pool_size: 4
        pool_mode: "session"
```

Полезно, когда одному пользователю (инструменты эксплуатации, миграции) нужна семантика сессии, а основное приложение остаётся в транзакционном режиме.

## Очистка при возврате в пул

По умолчанию `cleanup_server_connections` равен `adaptive`.
В сессионном режиме соединение возвращается в пул после отключения клиента.
В транзакционном режиме оно возвращается после завершения транзакции или autocommit-запроса.
Внутри открытой транзакции и во время `Flush` очистка не выполняется.
Если клиент оставил транзакцию открытой, сначала выполняется отдельный `ROLLBACK`, даже в режиме `off`.

Обычный `SELECT` не запускает очистку. Уже назначенная очистка при этом не отменяется.
Успешные `Parse` и `Bind` при включённом кешировании сами по себе не запускают очистку.
Кеш подготовленных запросов серверного соединения остаётся доступен для повторного использования.
Когда требуется встроенная очистка, pg_doorman сначала выполняет `RESET ROLE`, а затем нужные команды в таком порядке:

- После ответа `SET` выполняется `RESET ALL`.
- Если регистрация буферизованного `Parse` в кеше осталась незавершённой при возврате соединения, выполняется `DEALLOCATE ALL`.
- Если после вытеснения записи из кеша остался неотправленный `Close`, выполняется `DEALLOCATE ALL`.
- После ошибки PostgreSQL при включённом кеше подготовленных запросов серверного соединения требуется `DEALLOCATE ALL` перед повторным использованием соединения. Непригодное соединение закрывается.
- После `DECLARE CURSOR` выполняется `CLOSE ALL`, если клиент ещё не выполнил `CLOSE ALL`. Закрытие отдельного курсора не отменяет эту очистку.

Именованный `Parse` без управляемого кеширования требует всех трёх видов очистки. Это относится и к сессионному режиму.
Во время встроенной очистки `DEALLOCATE ALL` удаляет записи из LRU подготовленных запросов серверного соединения.
Эта внутренняя очистка не затрагивает кеш определений запросов пула и соответствия имён подготовленных запросов клиента.

У встроенной очистки есть ограничение. Любой ответ с тегом `RESET` отменяет `RESET ALL`, даже после сброса одного параметра.
Ответ `DISCARD ALL` сбрасывает признаки очистки параметров, подготовленных запросов и курсоров. Он также очищает LRU серверного соединения.
Незавершённая регистрация `Parse` и неотправленные `Close` проверяются отдельно при возврате соединения.
Если задан `cleanup_server_query`, pg_doorman выполняет его вместо встроенных команд.
Тогда `RESET` не отменяет очистку после `SET`, а клиентский `DISCARD ALL` требует выполнения настроенного запроса.

Режим `always` требует `cleanup_server_query` и выполняет его при каждом возврате использованного соединения.
Он добавляет команды серверу и требует заново подготовить запросы, удалённые из LRU серверного соединения.
Режим `off` пропускает SQL очистки сессии. Отдельный `ROLLBACK` сохраняется.

Adaptive-очистка отдельно не отслеживает SQL `PREPARE`, временные объекты, `LISTEN` и эффекты функций.
`RESET ALL` не освобождает advisory-блокировки. Выбирайте SQL очистки под ресурсы, которые использует приложение.
Для PostgreSQL с высокой частотой запросов и повторным использованием prepared statements можно оставить `adaptive` без `cleanup_server_query`.

Правила выбора [настроек general и пула](../reference/general.md#формат-конфигурационного-файла) описаны в справочнике.
Старые `true` и `false` означают `adaptive` и `off`. После RELOAD подключённые клиенты сохраняют прежнюю политику.
